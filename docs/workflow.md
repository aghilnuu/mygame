# 制作流程

1. 阅读最新企划与本地修改，复述阶段范围、目标、工具和验收标准。
2. 用户确认并下达阶段开始指令。
3. 执行已批准工作。缺少工具时提醒并负责安装，确需用户完成的账号或系统操作再单独说明。
4. 检查运行、相关交互及本次改动，提供明确的已完成内容与限制。
5. 按本阶段约定安排用户试玩验收；若约定先验收后推送，则修复反馈并通过验收后再提交。
6. 清理本阶段临时残留，提交并推送 GitHub，报告版本和实际结果。已获确认的步骤不重复申请。

## 项目记录与状态核对

- 项目文件是长期协作依据。用户已取消接入其他模型的计划，不再维护单独的模型切换接续文件。
- 恢复上下文或继续工作时，先读 `AGENTS.md`，再读取本次任务相关的需求、开发记录和代码；检查 Git 状态与最近提交，识别用户未提交的改动。
- 根据当前任务核对最新用户消息。需要读取企划时读取项目内的最新文档；用户仍在创作的内容不自动视为已获实施授权。
- 确认规则记入 `docs/requirements.md`；实现、验证、版本变化以及当前阶段、待办、验收与推送状态记入 `docs/development_log.md`。在这些状态变化时同步更新，避免维护互相矛盾的副本。
- 项目记录保留具体剩余工作、验证结果和已知限制；未运行的检查不写成通过，未获用户确认的方案不写成定案。工具可用性有变化时先验证当前任务所需能力。
- 出现记录冲突时，以用户最新明确指令决定设计，以代码、检查结果和 Git 状态判断实现进度。已有信息能消除冲突时直接修正记录；会影响设计且证据不足时再向用户澄清。

## 新对话交接

- 在阶段收尾及下一阶段规划时评估是否适合新建对话。若历史规则多次变更、上下文整理后出现遗漏或反复核对、话题混杂，或下一阶段任务较独立，则主动提醒用户并说明判断依据；不声称能准确测量未显示的上下文余量。
- 用户确认更换对话后，再制作交接文档及可直接用于新对话的启动说明。当前新增的是长期流程，不代表已确认立即交接或启动下一阶段。
- 交接前核对最新用户指令、相关企划、实际代码与 Git 状态。文档写明核对日期、正式仓库位置、分支与提交、未提交改动的归属，以及哪些信息尚未核验；不覆盖或擅自提交用户创作。
- 交接内容包括项目定位与制作路线、协作偏好及授权范围、已确认机制及关键更改理由、当前实现与代码入口、临时规则和已知限制、已完成及已验收内容、测试入口与实际验证结果、工具和启动方法、下一阶段目标及验收条件、待办和需要用户决定的问题。明确区分设计与实现、建议与定案、历史验证与本次验证，避免遗漏影响开发的细节。
- 以已有需求和开发记录为依据，交接文档提供清晰的阅读入口及必要的背景解释；完成后检查文档一致性与引用，按现有约定提交推送，并向用户提供文档位置与新对话启动说明。
- 新对话先读取协作规则、交接文档和相关项目文件，复核当前状态并简要复述目标、约束及下一步；已有授权继续有效，新阶段仍遵守阶段确认流程。发现资料缺失或冲突时先核实，不能保证自动继承旧对话全部历史。

## 代码维护

在每阶段收尾时检查本阶段影响到的旧代码。新增一批角色、怪物或卡牌之前，以及同一规则反复修改或试玩出现卡顿时，提前检查相关模块。先运行适用的战斗规则、交互和探索路线检查，再复现具体问题。把已发生的错误、妨碍内容扩展的写法和需要测量的性能问题分别记入开发记录。按影响大小安排小范围优化，并用同一操作或测试比较改动前后。数值平衡另按用户的试玩反馈处理。

## 阶段顺序

1. 开发环境、工程基础、启动界面。
2. 核心网格战斗、指令队列、移动与流逝，确认规则后扩展攻击与连招。
3. 房间探索、交互、门与传送门、探索战斗衔接。
4. 第一个可完整试玩的梦境与 Boss。
5. 美术动画音效完善及更多角色与内容。

每阶段开始前由助手提出具体可运行成果和验收步骤；本顺序是制作路线，不代表后续阶段已获执行授权。

能量在完成一名正式角色并完整跑完一局后另行接入；武器放在项目后期。局外完整主界面另设阶段，数值平衡在用户试玩并提出异常后处理。
