# 制作流程

1. 阅读最新企划与本地修改，复述阶段范围、目标、工具和验收标准。
2. 用户确认并下达阶段开始指令。
3. 执行已批准工作。缺少工具时提醒并负责安装，确需用户完成的账号或系统操作再单独说明。
4. 检查运行、相关交互及本次改动，提供明确的已完成内容与限制。
5. 按本阶段约定安排用户试玩验收；若约定先验收后推送，则修复反馈并通过验收后再提交。
6. 清理本阶段临时残留，提交并推送 GitHub，报告版本和实际结果。已获确认的步骤不重复申请。

## 模型切换与工作接续

- 项目文件是长期接续依据。使用内置模型或插件 API 接入模型均沿用本流程。
- 切换模型、恢复上下文或重新接续时，先读 `AGENTS.md` 与 `docs/handoff.md`，再读取本次任务相关的需求、开发记录和代码；检查 Git 状态与最近提交，识别用户未提交的改动。
- 根据当前任务核对最新用户消息。需要读取企划时读取项目内的最新文档；用户仍在创作的内容不自动视为已获实施授权。
- 确认规则记入 `docs/requirements.md`；实现、验证和版本变化记入 `docs/development_log.md`；当前阶段、已授权工作、待办、验收与推送状态记入 `docs/handoff.md`。在这些状态变化时同步更新，避免维护互相矛盾的副本。
- 接续说明保留具体剩余工作、验证结果和已知限制；未运行的检查不写成通过，未获用户确认的方案不写成定案。工具可用性有变化时先验证当前任务所需能力。
- 出现记录冲突时，以用户最新明确指令决定设计，以代码、检查结果和 Git 状态判断实现进度。已有信息能消除冲突时直接修正记录；会影响设计且证据不足时再向用户澄清。

## 代码维护

在每阶段收尾时检查本阶段影响到的旧代码。新增一批角色、怪物或卡牌之前，以及同一规则反复修改或试玩出现卡顿时，提前检查相关模块。先运行适用的战斗规则、交互和探索路线检查，再复现具体问题。把已发生的错误、妨碍内容扩展的写法和需要测量的性能问题分别记入开发记录。按影响大小安排小范围优化，并用同一操作或测试比较改动前后。数值平衡另按用户的试玩反馈处理。

## 阶段顺序

1. 开发环境、工程基础、启动界面。
2. 核心网格战斗、指令队列、移动与流逝，确认规则后扩展攻击与连招。
3. 房间探索、交互、门与传送门、探索战斗衔接。
4. 第一个可完整试玩的梦境与 Boss。
5. 美术动画音效完善及更多角色与内容。

每阶段开始前由助手提出具体可运行成果和验收步骤；本顺序是制作路线，不代表后续阶段已获执行授权。

能量在完成一名正式角色并完整跑完一局后另行接入；武器放在项目后期。局外完整主界面另设阶段，数值平衡在用户试玩并提出异常后处理。
